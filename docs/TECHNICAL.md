# Technical notes

How the Jump mod works and what we learned about jumping in Minecraft Dungeons (v1.17.0.0, UE 4.22, Steam). The general modding constraints (Blueprint only, Blueprint Loader levels, no UE4SS, no `PrintString`) are the same as ThirdPersonCam's; see its `docs/TECHNICAL.md`.

## Assets
| Asset | Role |
|---|---|
| `BPLoader/InGame/JMP_Ingame`, `BPLoader/Lobby/JMP_Lobby`, `BPLoader/Menu/JMP_Menu` | Loader levels with one `BP_JumpProbe` at the origin (made with `BPTool newlevel`). The menu one makes the binding changes before the first camp or mission loads. |
| `Mods/Jump/BP_JumpProbe` | All runtime logic, generated by `tools/blueprint/gen.py` |
| `Mods/Jump/W_JumpDebug` | Debug text (copy of AnalogMove's `W_AMDebug`, Text Block `DebugText`) |

## BP_JumpProbe
**BeginPlay**
1. `Delay 0.5`, `PC = GetPlayerController(0)`, `EnableInput(PC)`. Only with `DEBUG = True` in `gen.py` (off in releases): create `W_JumpDebug` and add it to the viewport.
2. **Roll remap:** `GetInputSettings → RemoveActionMapping(DodgeForward, SpaceBar)`, then `AddActionMapping(DodgeForward, R)`.
3. **Chat wheel:** `AddActionMapping(QuickActions, Gamepad_DPad_Left)`, because LT is taken for jumping.

All three use `bForceRebuildKeymaps = false` (see the findings for why). The changes live on the InputSettings CDO for the whole session, in memory only (never saved to the ini), and the game's own rebuilds pick them up. Repeating them on later levels does nothing new: the remove finds nothing, and the add skips duplicates. Nothing touches InputSettings in EndPlay (ThirdPersonCam crashed on quit doing that).

**Jump keys:** Space and LT, both with `bConsumeInput = true`. That stops Space from rolling (and from interacting or skipping; Left Mouse still interacts) and stops LT from opening the chat wheel. Each key stores its name in `LastKey`, then both run the same path:
1. `Char = GetPlayerCharacter(0)`. If `CharacterMovement.IsMovingOnGround` is false, ignore the press, so you can't chain jumps in the air.
2. `v = sqrt(2 × |CharacterMovement.GetGravityZ()| × JUMP_HEIGHT)`, with `JUMP_HEIGHT = 250`. `CharacterMovement.JumpZVelocity = v`.
3. Store `GroundZ = Peak =` actor Z, for the readout.
4. If `Char.CanJump()`, call `Char.Jump()`. Otherwise call `Char.LaunchCharacter((0, 0, v), XYOverride = false, ZOverride = true)`. Both give the same height.

**Key released** → `StopJumping`.

**Tick** → `Peak = max(Peak, actor Z)`, then, if `Dbg` is valid, the readout: CanJump, NavAgent `bCanJump`, on ground / falling / movement mode, JumpZVelocity, GravityZ, GravityScale, height, vertical speed, last jump peak (`Peak − GroundZ`), which path the last press took, jump/launch counters, and the remap status.

## Game internals (findings)
- **The hero is a normal `ACharacter`.** `BP_AlexCharacter` → `BP_PlayerCharacter` → native `DungeonsCharacter`, with a `CapsuleComponent` root and a `PlayerCharacterMovementComponent` (`CharMoveComp`). So `Jump`, `StopJumping`, `CanJump`, `LaunchCharacter` and the `CharacterMovement` properties all work from Blueprint with no stub.
- **No jump input exists.** `DefaultInput.ini` has no Jump mapping. Space is bound to `DodgeForward`, `Interact`, `MenuSelect`, `MenuSelectKeyboard` and `Skip`; the plain `Dodge` is on `ThumbMouseButton` (Mouse 4). R is used only by the menu actions `MenuResetSettings` and `ResetVR`, so it's free during gameplay.
- **Nothing native blocks jumping.** The hero walks in `MOVE_Walking` (mode 1, not NavWalking), `NavAgentProps.bCanJump` is true (the navmesh agent `LovikaDefault` has `bCanJump=False`, but that only affects pathfinding), and `Jump()` switches to `MOVE_Falling` (mode 3). The AnimBP already has a `Falling` state (`Player_Master_Falling`), so the hero gets a falling pose for free.
- **`CanJump()` is sometimes false while standing on the ground**, with the same readout values as when it's true. The cause is unknown: maybe an override in `BP_PlayerCharacter` (not exported) or jump-count state. The `LaunchCharacter` fallback hides it.
- **Gravity is about 5× standard.** `GetGravityZ()` ≈ −5000 (UE default −980) with `GravityScale = 1`, so the world or movement component has its own gravity. The default `JumpZVelocity = 1000` only gave about 100 units (≈1 block), and a 600 launch about 35. That's why the take-off speed is computed from the live gravity.
- **Scale:** a 200-unit peak looked like exactly 2 blocks in camp, so 1 block ≈ 100 units. 250 (2.5 blocks) felt best, close to Minecraft Dungeons II's jump.
- **The game adds bindings at runtime, for keyboard and controller.** `DefaultInput.ini` has no RB mapping for the forward roll, yet RB rolls, and `QuickActions` (the quick-chat wheel, LT) is listed with `Key=None`. Space → `DodgeForward` is also added again at runtime, probably from the in-game Customize Controls settings. `RemoveActionMapping` therefore can't take any of these away. **Consuming the key works instead:** an actor key event with `bConsumeInput = true` (our input component sits above `BP_PlayerController`'s) stopped RB, Space and LT from reaching the game. `InputSettings.AddActionMapping` still adds extra keys to those actions (R rolls, D-pad Left for the wheel).
- **Never call `InputSettings` with `bForceRebuildKeymaps = true`.** It runs `PlayerInput.ForceRebuildingKeyMaps(bRestoreDefaults = true)`, which resets every player to the ini defaults and drops the runtime bindings. On entering camp, only the left stick (an ini axis) and our own LT worked, until a mouse click made the game re-apply its bindings. (It's also why the first Space → R remap seemed to work: it had wiped the runtime Space → roll binding.)
- **A is melee and can't be moved.** In Dungeons 1, A = melee / interact / elytra dive. There's no named action for melee, so Minecraft Dungeons II's A = Jump, X = Melee layout isn't possible. The free buttons in gameplay are LT (chat wheel, online only), L3 and D-pad Left. D-pad Right is Emote, Up is inventory, Down is the map.
- **The chat wheel only opens online.** `BP_PlayerController.CanOpenChatWheel` checks `IsInOnlineGame` / `IsOnlineSession`, so LT does nothing in single player, which made it the natural jump button.
- **Attacking mid-air works.** Melee and ranged attacks play during a jump. Most weapons have no air animation, so it looks odd, but the hammer's swing looks like a slam.

## Testing so far
Camp, keyboard and mouse: jumping, jump height (200 measured, then raised to 250), attacking mid-air, and the roll remap (R rolls, Space no longer does).
Camp, controller: RB jumped and stopped rolling when consumed (an earlier probe); LT jumps; every button works right after the camp loads.
Current build, from a fresh start: Space jumps, R rolls, controller works in camp.

**Untested:** the chat wheel on D-pad Left and its removal from LT. Both only show up in an online game.
